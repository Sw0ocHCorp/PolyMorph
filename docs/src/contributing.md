# Extending this documentation

This book is meant to grow one pipeline at a time. The conventions below keep it consistent.

## Structure

```
src/
├── framework/      the general stack — anything every pipeline uses
├── math/           mathematical concepts, one page per family of ideas
├── pipelines/
│   └── <name>/     one directory per robotics pipeline
│       ├── overview.md            data flow, contracts, status
│       ├── <component>.md         one page per component
│       ├── roadmap.md             what is not built yet, and why it belongs there
│       ├── validation.md          the acceptance ladder and its numeric criteria
│       └── lessons.md             bugs met, their mechanism, the rule that follows
├── simulation/     bridges to simulators and hardware
└── glossary.md
```

A new pipeline (perception, navigation, planning) gets its own directory and its own part in `SUMMARY.md`. Mathematics **shared** by several pipelines goes to `math/`; mathematics **specific** to one pipeline stays inside it.

## Writing rules

- **English**, like the source comments. The code is the reference for names; prose explains why.
- **Every symbol used in a formula is defined**: its type and shape (scalar, 3-vector, matrix), its unit, its frame, and the code field that carries it. A pointer to a field is not a definition — and if the field's name is misleading, say so explicitly. Add it to the [glossary](glossary.md).
- **State the *why*, not just the *what***. The code already says what happens; the book exists for the reasoning that produced it, and for the alternatives that were rejected.
- **Numbers belong in tables**, not in prose.
- **A rule learnt from a bug goes in two places**: the mechanism in the component's page, the symptom → cause → rule row in `lessons.md`.

## Diagrams

Diagrams are **inline SVG**, written by hand in the Markdown, wrapped in `<figure>` with a `<figcaption>`:

- give the `<svg>` the class `diagram` and a `viewBox` (700 units wide is the book's text width);
- use `currentColor` for text and neutral strokes so the figure follows the light/dark theme; accent colours `#4a90d9` (blue), `#2aa198` (teal), `#cb8b1e` (amber), `#d4694a` (coral), `#8b7cd8` (purple) read on both backgrounds;
- fill boxes with `fill="currentColor" fill-opacity="0.06"` rather than a fixed colour;
- **marker ids must be unique per page** (`p-arw`, `s-arw`, …): ids are global in the rendered HTML;
- add `role="img"` and `aria-label` describing what the figure shows.

Curves that come from a formula (step responses, trajectories) are generated by a short script rather than drawn by hand, so they stay honest.

> Inline SVG does not render in GitHub's Markdown viewer. Read the book with `mdbook serve`, or link to the built site.

## Building

```bash
cargo install mdbook      # once
cd docs && mdbook serve --open
```

`mdbook build` writes the static site into `docs/book/`, which is git-ignored.

## Keeping the book and the code in step

The source comments carry the *local* reasoning (why this line, this guard, this order) and point here for the theory. This book carries the *global* reasoning. When a design decision changes:

1. update the component page and, if the decision is architectural, `framework/conventions.md`;
2. update the affected `// NOTE:` comments in the code;
3. if a bug motivated the change, add the row to the pipeline's `lessons.md`.
