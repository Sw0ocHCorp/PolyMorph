# Messages and data types

Files: `robomorph/src/messages/*.rs`.

## `AnyMessage` and transport

`AnyMessage` is the single enum that travels on every broadcast channel and through the scheduler pipe:

| Variant | Payload | Producer → consumer |
|---|---|---|
| `PoseState(Pose)` | vehicle state (attitude, IMU, GNSS…); the same struct is the **setpoint** that goes down the control cascade, see below | vehicle controller → stages, UDP; scenario player → velocity → resolver → attitude (pipe) |
| `VehicleWrench(WorkVec)` | wrench to produce, body frame, N / N·m | attitude → mixer (pipe) |
| `MotorCommands(Vec<MotorCommand>)` | per-motor commands, in efforts | mixer → vehicle controller |
| `MotorState(MotorState)` | one motor's last feedback and last command | reserved for external transport (an interface displaying the vehicle) |
| `ImuState`, `GnssState`, `LidarState` | raw samples | outward |
| `RemoteControl` | gamepad state | remote → (unused today) |

### The setpoint `Pose` down the cascade

One message travels through the pipe from the mission to the attitude stage: a `Pose`. Each stage **reads** the fields it needs and **fills** the fields it produces, then hands it on. Any process may stand before a stage, as long as it fills the fields that stage reads: a gamepad stage that sets an attitude and a thrust could feed the attitude stage directly.

| Field | Content | Frame / unit | Filled by | Read by |
|---|---|---|---|---|
| `orientation` | `q_pref` (mission), then `q_d` | body → world | mission, then resolver | resolver, attitude |
| `l_velocity` | `v_d`, desired velocity | world, m/s | mission | velocity (brick 5) |
| `imu_measurement.a_velocity` | `ω_d`, desired angular rate | body, rad/s | mission (zero), then resolver | attitude |
| `force` | `f_d`, desired force, weight compensation included | **world**, N | velocity | resolver, attitude |

A stage **abstains** (`None`) when a field it reads is missing [P3]; the next stage then holds its last setpoint. In a measured state, `force` is `None`: it is a setpoint field only.

> **Pitfall.** `from_frame` slices off the first byte without checking it and without checking the length: an empty datagram panics, and a frame whose tag does not match the target type is decoded anyway. `MotorModel` and `RemoteControl` can be encoded but are never decoded by `decode_frame`.

## Base types

- **`Vec3`** wraps `nalgebra::Vector3<f64>` with `Deref` (all nalgebra methods are reachable) and a hand-written `prost::Message` impl. Careful: `*` and `/` between two `Vec3` are **element-wise**.
- **`UnitQuat`** is the wire form of a unit quaternion, fields **`w, x, y, z`** (w first). Its `Default` is the **identity**: the derived default `(0,0,0,0)` has zero norm and normalising it yields `NaN`. Converting to `UnitQuaternion` renormalises.

> nalgebra stores and *prints* quaternion coefficients as `(i, j, k, w)` — w **last**. A nalgebra debug print of `[0, 0, 0, 1]` is the identity, not a 180° yaw. Two conventions coexist in the logs; label them.

- **`WorkVec`** is the 6D wrench `[fx fy fz mx my mz]`, body frame, moments about the centre of mass. Arithmetic operators are generated by a macro (`+ − * /` by a scalar, `Sum`). It is a plain struct, never on the wire.

## `Pose`

The aggregated vehicle state. Fields used by control:

| Field | Content | Frame / unit |
|---|---|---|
| `orientation` | attitude `q`, body → world | — |
| `imu_measurement.a_velocity` | gyroscope angular rate `ω` | body, rad/s |
| `imu_measurement.l_accel` | specific force (norm ≈ 9.81 when supported, ≈ 0 in free fall) | body, m/s² |
| `gnss_measurement` | lat / lon / alt | world |
| `l_velocity` | **estimated** linear velocity (not a raw measurement) | — |

The **same** struct is used as the attitude controller's **setpoint**, where only `orientation` (the desired attitude `q_d`) is read. The desired angular rate is implicitly zero in the current implementation, so the setpoint's `a_velocity` is not consumed yet.

`Transform` (`location`, `orientation`) is a motor's *resolved* pose in the body frame, computed by `MotorTree::transforms`. It is internal and never serialised.

## The motor model

### `MotorModel` — one node of the kinematic tree

The **description** of a motor, configured once inside the shared `MotorTree` (see [the motor model](../pipelines/motor-control/motor-model.mdx#one-tree-configured-once-shared-by-every-stage)), which also reads it from a JSON file.

| Field | Meaning |
|---|---|
| `id`, `parent_id` (0 = root, mounted on the airframe) | tree topology; the children are derived from `parent_id` by the `MotorTree` |
| `relative_location`, `relative_orientation` | pose **at rest**, in the **parent's** frame (root: vehicle frame; the CoM offset is applied at use). A joint's current angle is not in there. |
| `working_axis` | the motor's **family** — see below |
| `min_value`, `max_value` | bounds of the motor's own effort: rad for a joint, N for a thruster |
| `effort_constant` `k`, `exp_command_law` `n`, `transmission_factor` | effort law `T = transmission · k · ωⁿ` (propeller: n = 2) |
| `moment_constant` `k_m` | reaction torque on the airframe per newton, along the thrust axis, **signed** by the spin direction: negative for a rotor spinning counter-clockwise about that axis, positive for a clockwise one |
| `max_rot_speed` | rotor speed ceiling for a thruster; for a joint, the angular speed used as the allocation's **trust region** per cycle |

### The two families

`WorkingAxis` splits motors into two families of different natures:

| | Angular joint (`RotatingAround{X,Y,Z}`) | Thruster (`LinearMotionAlong{X,Y,Z}`) |
|---|---|---|
| Decision variable | an angle (rad) | a thrust (N) |
| Produces a wrench? | no — it **reorients** its children's | yes |
| Effectiveness column | tangent `dw/dθ`, proportional to its children's thrust | exact, purely geometric |
| Command emitted | `ANGULARPOSITION` (rad) | `THRUST` (N) |

> The family is read with `MotorModel::is_joint` / `is_thruster`. `WorkingAxis::Unknown` (0) belongs to neither, and `MotorTree::new` refuses a motor that has it.

### `MotorFeedBack`, `MotorCommand` and `MotorState`

One role per message: a feedback only measures, a command only asks.

`MotorFeedBack` (`timestamp`, `id`, `status`, `current_value`): `current_value` is the **current effort in mixer units**, thrust `T` in newtons for a thruster (reconstructed from the measured rotor speed through the effort law), angle in radians for a joint. `status` (`MotorStatus`: `IDLE`, `RUNNING`, `ERROR`) is the motor's state as the source of the measurement reports it: the Gazebo bridge reports `RUNNING`, an IO board would report a fault.

`MotorCommand` (`timestamp`, `id`, `command_type`, `setpoint_value`): the only place a setpoint lives. `command_type` **declares the unit** of `setpoint_value`: `THRUST` = N, `ANGULARPOSITION` = rad, `VELOCITY` = rad/s. The N → rad/s conversion happens at the hardware boundary, never in the mixer.

`MotorState` (`id`, `feedback`, `command`) is the runtime state of one motor: its last feedback and its last command, each absent until the first. `MotorState::record_measurement` refuses a non-finite measurement; `MotorState::get_command` brings the setpoint inside the motor's bounds and picks its unit from the motor's family.

## Vehicle configuration

`VehicleKinematicConfig` (in `motion_controller.rs`) is the vehicle's **physical identity card**: `weight` (mass, kg), `moments_matrix` (the total inertia matrix, kg·m²), `com_relative_location`. It is purely physical — controller tunings such as `τ` do not belong in it; a tuning belongs to the component that uses it. The `error_*_factor` fields are leftovers, unread by the current chain.

> `moments_matrix` holds **moments of inertia**, not moment-torques. The name is a trap: see [Rigid-body efforts](../math/rigid-body.mdx).
