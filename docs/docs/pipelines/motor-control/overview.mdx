# Motor control: overview

The first robotics pipeline of the stack. It answers one question: **given a desired attitude, what command should each motor receive?**

## Data flow

<figure>
<Diagram1 />
<figcaption>Solid arrows: the scheduler pipe, within one pass. Dashed arrows: broadcast channels.</figcaption>
</figure>

All the processes run in the **same processes pipeline at 100 Hz**, registered in this order: `osprai → remote → scenario_player → velocity → resolver → attitude → mixer → recorder` (on the bench, the resolver is in the cascade only for the scenarios that ask for it). That guarantees one fresh measurement per tick and makes the pipe reliable — see [Conventions](../../framework/conventions.mdx). The cascade hands **one** setpoint `Pose` down the pipe, each stage enriching it — the velocity stage adds the force `f_d`, the resolver sets `q_d` and `ω_d` — and the attitude stage turns it into the wrench (see [the setpoint `Pose` down the cascade](../../framework/messages.mdx#the-setpoint-pose-down-the-cascade)). The bridge only measures and actuates; the mission setpoint comes from the scenario player, the single source of setpoints, at the head of the cascade; the recorder (optional) writes one CSV row per pass — see [Running scenarios](../../simulation/running-scenarios.mdx).

## Stage contracts

| Stage | Measurement | Setpoint | Output | Frame |
|---|---|---|---|---|
| [Velocity stage](roadmap.mdx#velocity-loop) (`VelocityController`) | `v`, in `l_velocity` of the telemetry (odometry), with its time stamp | setpoint `Pose` (mission): `v_d` in `l_velocity`, optional | the same, plus `force` = `f_d = m·(a_d + g·ẑ)`; `a_d` = PI on `v_d − v` when `v_d` is given, 0 otherwise | world |
| [Force → attitude resolver](resolver.mdx) | — | setpoint `Pose`: `force`, `orientation` (`q_pref`) | the same, with `orientation` = `q_d`, `ω_d` | world / body |
| [Attitude controller](attitude-controller.mdx) | `q`, `ω` (IMU) | setpoint `Pose`: `q_d`, `ω_d`, `f_d` | wrench `[q⁻¹·f_d ; M]` | body |
| [Mixer](mixer.mdx) | motor feedbacks (efforts) | wrench | one command per motor | body → per-motor |
| [Vehicle controller](../../simulation/gazebo.mdx) | — | motor efforts | actuator units | hardware |

The **wrench** is the contract that makes each side replaceable: the mixer does not know what commands it, the attitude stage does not know which vehicle executes it.

## What exists and what does not

| | Status |
|---|---|
| Attitude loop | built, validated on the scenario bench (`roll_step`) |
| Control allocation over an arbitrary motor tree | built, validated on the OSPRAI |
| Velocity loop | [built](roadmap.mdx#velocity-loop) (brick 5a): a PI on the velocity with the generic `PIDController<Vec3>`, `τ_v = 2 s`, running only when the setpoint carries `v_d`; without it the stage supplies the weight compensation alone, `f_d = (0, 0, m·g)`. validated on the scenario bench (`velocity_hold`, `velocity_step_y`); anti-windup and saturations in brick 5b |
| Force → attitude resolver | [built](resolver.mdx) for aerial vehicles: `S` from the motor tree, alignment for k = 1, 2, 3; ground vehicles and the tilt limit pending |
| Position loop | [planned](roadmap.mdx) |
| Arming / spool-up sequencing, failsafe, data-age supervision | not started — belongs to a supervisor |

## The one-cycle delay

Commands computed in pass *k* are applied in pass *k+1*: the vehicle controller drains the command channel at the start of its `exec`. Every discrete controller pays a computation delay somewhere; putting it on actuation rather than measurement keeps the critical loop reading the freshest possible state, and it is covered by the `τ ≥ 10·T` margin.
